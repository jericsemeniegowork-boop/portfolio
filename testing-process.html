How Testing Gets Done

Testing Approach

Six steps, same order every time. Read, write, run, log, retest, report.

The Six Steps

Applied consistently across SAP testing at Accenture, freelance client work, and all portfolio case studies.

01

Read the Workflow First

Before writing a single test case, read the ticket, the business flow document, or the QMS reference to understand what the system is actually supposed to do, not just what the screen shows.

  • What steps does the process follow?
  • What data does it read or write?
  • What role or permission is involved?
02

Write the Test Cases in Excel

Build the test case list in Excel before opening the system. Group by workflow area, cover the happy path first, then add negative and edge case scenarios, pulled into an RTM to confirm every requirement has at least one test.

  • Functional checks
  • Negative and boundary checks
  • Regression checks on anything that changed
  • UAT scenarios for business sign-off
03

Run Each Test Exactly as Written

Follow the test steps precisely, compare what the system does against the expected result, and mark each case Pass, Fail, or Blocked in the execution sheet, with the actual result noted every time, not just the status.

  • Actual result recorded even on Pass
  • Evidence captured when a step fails
  • Blocked items documented with the reason
04

Log Every Defect in ServiceNow or Jira

Every failed test gets a defect report, replication steps, the expected result, the actual result, severity, and a screenshot from Browser DevTools if there is a console error or a failed API call visible in the Network tab.

  • Steps to reproduce numbered clearly
  • Expected vs. actual result
  • Severity and priority set
  • Screenshot or screen recording attached
05

Escalate or Retest After the Fix

If a fix needs a developer, escalate the ticket in ServiceNow or Jira with all the evidence already attached. When the fix comes back, retest the exact failing steps, then run a quick regression on anything connected to make sure nothing else broke.

  • Patch and reset validation
  • Retest only after fix is confirmed in the right environment
  • Regression scope covers related workflows
06

Write Up the Test Summary

Put the results in an Excel test summary, total cases, passed, failed, blocked, open defect count with severities, and any outstanding risks. This is what supports the release sign-off conversation.

  • Pass rate calculated
  • Open defects listed with current status
  • Release recommendation included
Testing Methods Used

Types of checks applied during test case design and execution.

Functional Testing

Each feature or workflow step is run to confirm it does what the requirement says. If the system does something the requirement does not describe, that gets logged.

e.g. submitting a filing request, approving a workflow, generating a document

Regression Testing

After a fix or patch goes in, existing test cases are re-run to confirm the change did not break anything that was previously working. Selenium scripts run the stable ones automatically.

e.g. re-running SAP workflow checks after a patch deployment

UAT Support

Business users run through real scenarios and the QA role is to document what they find, confirm reported issues are reproducible, and support the sign-off process.

e.g. confirming an SAP process works for the actual business team before release

Negative Testing

Inputs that should fail are tested to confirm the system handles them correctly, missing required fields, wrong data types, and unauthorized access attempts all get checked.

e.g. submitting a form with empty required fields, testing an endpoint with a missing auth token

Data Validation with SQL

After a workflow completes in the UI, SQL queries are run directly against the database to confirm the correct values were saved, not just that the screen said success.

e.g. checking that a status field updated correctly and a history record was written after an SAP step

API Testing with Postman

API endpoints are tested independently of the UI using Postman, checking status codes, response body data, error messages, and authentication handling with JavaScript test scripts.

e.g. confirming an endpoint returns 200 with the right data and 400 for bad input
