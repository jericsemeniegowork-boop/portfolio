How Testing Gets Done

Testing Approach

A structured, repeatable approach: understand the flow, list what needs testing, execute the checks, document issues, escalate or retest, and summarize the result.

Core Focus

Clear test cases, accurate validation, clean tickets, and useful reports.

01

Understand the Workflow

The business flow, system document, QMS/process reference, blueprint, or ticket details are reviewed before testing begins to establish what the system is expected to do.

  • What is the expected behavior?
  • Who is the user or role involved?
  • What part of the system is affected?
02

List What Needs to Be Tested

A structured list of test scenarios and test cases is prepared before execution, avoiding ad-hoc testing.

  • Functional checks
  • Negative and boundary checks
  • Regression checks
  • UAT and business validation checks
03

Execute the Test Carefully

Each workflow is executed step by step, with actual behavior compared against expected behavior and results recorded.

  • Pass, fail, or blocked status
  • Actual result with notes
  • Evidence captured when needed
04

Log or Update the Ticket

Issues are documented clearly and thoroughly so any team member can understand and reproduce them.

  • Steps to reproduce
  • Expected vs. actual result
  • Impact, severity, and evidence when available
05

Escalate, Coordinate, or Retest

Issues requiring developer, business user, or cross-team involvement are escalated with full context. Affected workflows are retested after each fix or reset.

  • Patch and reset validation
  • Incident follow-up
  • Regression after each fix
06

Summarize the Result

Notes and reports are prepared to summarize what was tested, what passed, what failed, and what still requires attention.

  • Testing summary with metrics
  • Open risks or blockers
  • UAT or release readiness notes
Testing Methods Applied

Types of checks used when building test cases or validating a ticket.

Functional Testing

Checks if the feature or workflow behaves according to the requirement.

Example: request submission, approval flow, status update

Regression Testing

Checks if a change, fix, patch, or reset broke an existing workflow.

Example: retesting related SAP process steps after a patch

UAT Support

Confirms that the system works for business users and real workflow needs.

Example: preparing checks, notes, and feedback for business sign-off

Negative Testing

Checks how the system behaves with invalid, missing, or unexpected input.

Example: missing required field or unauthorized access attempt

Data / Status Validation

Checks that records, statuses, history, and system results are accurate.

Example: validating status mismatch between list and detail pages

Smoke / Sanity Checks

Quick checks to confirm a build, fix, or workflow is stable enough to continue testing.

Example: confirming the main flow works after a system reset
