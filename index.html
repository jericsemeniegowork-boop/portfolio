Manual vs. automated testing — my position

Manual testing Core strength

Manual testing is human-driven validation through direct interaction with the application, APIs, tickets, and test data. It is valuable for exploratory testing, usability review, UAT support, new feature validation, and checking real workflow behavior.

  • Best for unclear or changing requirements
  • Useful for business workflow validation
  • Strong for defect investigation and evidence capture
  • Matches my experience in regression, UAT, issue replication, and release validation

Automation testing Growth area

Automation uses scripts and tools to repeat stable checks faster. I understand that automation is useful for regression, smoke tests, and CI/CD pipelines, but the quality depends on clear scripts and stable test design.

  • Good for repetitive and stable scenarios
  • Useful for scaling regression coverage
  • Portfolio includes a simple Selenium/Python read-only check
  • I am open to growing into automation while contributing strongly in manual QA

Testing types shown in this portfolio

This section turns textbook testing terms into practical examples using my Purchase Request and Approval case study.

Testing TypeHow I use it in the portfolio
Functional TestingValidate create request, submit, approve, reject, status update, validation messages, and read-only behavior.
Smoke TestingQuickly confirm login, dashboard, purchase request module, and core workflow are accessible after deployment.
Sanity TestingFocused check after a specific fix, such as verifying that approved requests are no longer editable.
Regression TestingRerun impacted workflows after a change to confirm existing features still work.
End-to-End TestingRequester creates and submits a request, approver approves or rejects it, and final status/history are validated.
Acceptance / UATConfirm the workflow meets business expectations for requester and approver users.
Exploratory TestingTry unexpected actions such as double submit, browser back, missing fields, unusual amounts, and role switching.
Defect RetestingRetest fixed bugs using original reproduction steps and update the defect status based on results.
Performance AwarenessObserve slow page loads, delayed status updates, or repeated workflow instability and report concerns clearly.
Honest scope: Unit testing and deeper code-level white-box testing are usually developer-led. My focus is manual black-box/gray-box QA, with technical awareness through API, SQL, DevTools, and Selenium basics.

Manual QA process / STLC workflow

This is the process I follow and demonstrate through my uploaded QA artifacts.

Requirement Analysis

Review BRD, SRS, user stories, and tickets.

  • Identify testable requirements
  • Clarify ambiguity
  • Identify risks and dependencies

Test Planning

Define what will and will not be tested.

  • Scope and test types
  • Entry and exit criteria
  • Tools, environment, and timeline

Test Design

Create scenarios and detailed test cases.

  • Positive, negative, edge/boundary cases
  • Expected results
  • Requirement Traceability Matrix

Test Data Preparation

Prepare realistic and reusable data.

  • Valid and invalid inputs
  • Boundary values
  • Requester, approver, and unauthorized users

Environment Setup

Confirm QA/staging readiness.

  • Browsers and devices
  • Build deployed
  • Smoke check before full execution

Test Execution

Run test cases and record results.

  • Pass, Fail, Blocked
  • Actual result notes
  • Screenshots/videos when needed

Defect Management

Log issues clearly and track lifecycle.

  • Steps to reproduce
  • Expected vs actual
  • Severity and priority

Retesting + Regression

Confirm fixes and impacted workflows.

  • Retest fixed bugs
  • Run regression checks
  • Confirm no old features broke

Test Reporting

Summarize quality status.

  • Pass/fail rate
  • Defect count
  • Coverage, risks, and recommendation

Release Validation

Support release readiness and post-release checks.

  • Smoke checks
  • Known issues
  • Release recommendation
