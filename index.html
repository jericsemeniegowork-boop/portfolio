Testing Levels and Execution Types

These are common test levels and execution types I understand. I connect them to my portfolio where applicable, while keeping my strongest positioning as manual QA.

Unit Tests

Low-level tests close to the source code. They validate individual methods, functions, classes, components, or modules. These are usually developer-led and often automated because they are fast to run.

Concept awareness

Integration Tests

Verify that different modules, services, or systems work together, such as application-to-database interaction or service-to-service communication.

Supported by API/SQL awareness

Functional Tests

Focus on business requirements and expected output. They check whether a user action produces the correct result according to the requirement.

Used in portfolio

End-to-End Tests

Replicate a real user journey in a complete environment. Example: requester creates a request, submits it, approver approves it, and the system updates the status.

Used in portfolio workflow

Acceptance Testing

Verifies whether the system satisfies business requirements and user expectations. UAT is a common form of acceptance testing.

Used through UAT checklist

Performance Testing

Evaluates speed, reliability, scalability, and responsiveness under workload. As manual QA, I can observe slow pages, delays, timeouts, and report performance concerns.

Basic awareness

Smoke Testing

Basic health check to confirm that major features are working and the build is stable enough for deeper testing or post-deployment validation.

Used in process

QA Tools Utilized in Test Cases

This page shows how I used common QA tools inside the sample test cases, not just as a list of tools. The examples are representative and non-confidential: test management for execution, bug tracking for defects, Postman for API checks, BrowserStack for compatibility checks, automation tools for repeatable regression, and performance tools for baseline load validation.

Tool usage summary: grouped by practical QA use so recruiters can quickly see how each tool supports testing.

Test Management

Tools utilized: TestRail, Zephyr, Excel/Google Sheets.

How I used it in test cases: Organized test cases by module, priority, test type, expected result, actual result, and execution status. Example: banking TC-BANK-001 account balance validation and game TC-GAME-ECO-001 reward integrity were tracked as high-priority regression cases.

Used for test execution

Bug Tracking

Tools utilized: Jira, Bugzilla, Mantis, ServiceNow-style tickets.

How I used it in test cases: Logged failed cases with reproduction steps, expected vs actual result, severity, priority, evidence, environment, and retest status. Example: BUG-BANK-001 balance button does not load account balance was marked High severity due to direct customer impact.

Used for defect reporting

API Exploration

Tool utilized: Postman.

How I used it in test cases: Manually inspected API responses before automation. Example: verified that the account balance API returns only authorized customer data, correct status codes, masked sensitive fields, and consistent values between mobile and web.

Used for gray-box checks

Cross-Browser / Device Checks

Tool utilized: BrowserStack.

How I used it in test cases: Verified UI consistency across supported browsers, devices, and screen sizes. Example: checked banking account overview on desktop Chrome, desktop Edge, iOS Safari, and Android Chrome to confirm layout, text visibility, and balance display.

Used for compatibility testing

Web Automation

Tools utilized: Selenium, Playwright, Cypress.

How I used it in test cases: Identified stable regression candidates for automation, such as login smoke, purchase request submission, account overview load, and approved request read-only validation. These are repeatable flows that should run every release.

Used for regression candidates

Mobile Automation

Tool utilized: Appium.

How I used it in test cases: Mapped mobile regression coverage for banking login, account balance display, session timeout, and cross-app sync between mobile and desktop. Best used after the manual flow is stable and requirements are clear.

Used for mobile regression planning

Low-Code / No-Code Automation

Tools utilized: BugBug.io, Testim-style tools.

How I used it in test cases: Used as a fast way to record simple smoke flows, such as login, open dashboard, view account balance, or submit a sample request. I would still review recorded tests to reduce flaky steps and weak assertions.

Used for quick smoke candidates

Performance Testing

Tools utilized: Apache JMeter, LoadRunner.

How I used it in test cases: Planned baseline load checks for high-risk flows such as banking login, account overview, balance refresh, and transaction history retrieval. The goal is to measure response time, throughput, and behavior under normal and peak load.

Used for non-functional coverage
