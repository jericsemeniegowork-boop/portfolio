Testing Process

How I usually approach testing

I try to keep testing practical. First I understand the flow, then I list what needs to be tested, execute the checks, document the result, and escalate or retest when needed.

My focus Clear test cases, accurate validation, clean tickets, and useful reports.
01

Understand the workflow

I review the business flow, system document, QMS/process reference, blueprint, or ticket details so I know what the system is supposed to do before testing.

  • What is the expected behavior?
  • Who is the user or role involved?
  • What part of the system is affected?
02

List what needs to be tested

I prepare a clear list of test scenarios and test cases instead of testing randomly.

  • Functional checks
  • Negative and boundary checks
  • Regression checks
  • UAT/business checks
03

Execute the test carefully

I run the workflow step by step, compare actual behavior against expected behavior, and record the result.

  • Pass, fail, or blocked status
  • Actual result and notes
  • Evidence when needed
04

Log or update the ticket

If I find an issue, I document it clearly so the next person can understand and reproduce it.

  • Steps to reproduce
  • Expected vs actual result
  • Impact, severity, and screenshots/logs if available
05

Escalate, coordinate, or retest

For issues that need a developer, business user, or another team, I escalate with the right details. After a fix or reset, I retest the affected workflow.

  • Patch/reset validation
  • Incident follow-up
  • Regression after fix
06

Summarize the result

I prepare notes or reports that show what was tested, what passed, what failed, and what still needs attention.

  • Testing summary
  • Open risks or blockers
  • QMS/process documentation updates when applicable
  • UAT or release readiness notes

Testing methods I apply

These are the types of checks I use when building test cases or validating a ticket.

Functional Testing

Checks if the feature or workflow behaves according to the requirement.

Example: request submission, approval, status update

Regression Testing

Checks if a change, fix, patch, or reset broke an existing workflow.

Example: retesting related SAP process steps after a fix

UAT Support

Helps confirm that the system works for business users and real workflow needs.

Example: preparing checks, notes, and feedback tracking

Negative Testing

Checks how the system behaves when invalid, missing, or unexpected input is used.

Example: missing required field or unauthorized access

Data / Status Validation

Checks that records, statuses, history, and system results are accurate.

Example: validating incorrect data or failed workflow status

Smoke / Sanity Checks

Quick checks to confirm if a build, fix, or workflow is stable enough to continue testing.

Example: confirming the main flow works after a reset

Defect Sample

Back Button Navigation Redirects to Incorrect Page

Severity: Medium

Issue Description

During testing in a time management workflow, I observed that the Back button did not consistently return the user to the most recent page or panel previously accessed.

The issue appeared across multiple screens, which suggested a possible shared navigation handling problem.

Expected vs Actual

Expected: Clicking Back should return the user to the most recent page or panel in the current workflow.

Actual: In some cases, Back redirects the user to a different process or page instead of the last interacted screen.

Replication Steps

  1. Open the administrative module.
  2. Navigate to the time management workflow.
  3. Open a record or details screen.
  4. Click the Back button.
  5. Observe the destination page.
  6. Repeat on a related screen to confirm if the issue occurs in multiple flows.
Impact: This affects navigation accuracy, user experience, and test execution flow consistency. Since it occurs in multiple flows, it may require review of shared routing or navigation history handling.

Case Study

Purchase Request and Approval Management System

Testable Requirements

  • Requester can create a purchase request.
  • Required fields must block submission when missing.
  • Requester can submit a valid request for approval.
  • Approver can approve or reject a pending request.
  • Rejection must require a reason.
  • Approved requests must become read-only.
  • Request list and detail page must show the same status.
  • Request history must record important actions.
  • Unauthorized users must not access approval actions.

Clarification Questions

1. Can a requester approve their own request?

2. Which fields are required before submission?

3. Should rejected requests be editable and resubmittable?

4. What actions should appear in history/audit trail?

5. What are the release exit criteria?

Main Risks

  • Approved request remains editable.
  • Status mismatch between list and detail page.
  • Rejection without reason.
  • Missing audit/history record.
  • Unauthorized approval action.

BUG-001: Approved Request Remains Editable

**Module:** Purchase Request / Approval

**Severity:** High

**Priority:** High

Steps to Reproduce

1. Login as requester.

2. Open an approved request.

3. Try to edit the Amount field.

4. Click Save.

Expected Result

Approved request should be read-only and protected fields should be disabled.

Actual Result

Requester can still edit protected fields.

Impact

Can affect approval integrity, audit accuracy, and reporting.

---

BUG-002: Rejection Allowed Without Reason

**Module:** Approval Workflow

**Severity:** Medium

**Priority:** High

Steps to Reproduce

1. Login as approver.

2. Open pending request.

3. Click Reject.

4. Leave reason blank.

5. Confirm rejection.

Expected Result

System blocks rejection and requires a reason.

Actual Result

Request is rejected without reason.

Impact

Business users cannot see why the request was rejected.
