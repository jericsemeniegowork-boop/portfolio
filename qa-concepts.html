Testing Concepts & Proficiency

The testing categories I work across, organized the way they actually break down in practice. Each one has an honest proficiency tag based on real work history. Items I have not done hands-on are included for completeness but left unlabeled rather than padded.

11 Proficient 1 Working 1 Basic, growing 5 Reference
By Purpose: What the Test Is Checking

Functional Testing

Proficient

Checks the system behaves the way the requirements say it should.

Verifies that features produce the expected output for given inputs, against documented requirements or user stories. Does not concern itself with internal logic or performance, only correctness of behavior.

In my work: Daily work at Accenture across SAP S/4HANA and web release cycles, validating fixes against acceptance criteria.

Examples
  • Login produces a session on valid credentials
  • Order checkout creates a record with the expected total
  • A form rejects invalid email format

Non-Functional Testing

Working

Measures how well the system performs, not whether it works.

Covers performance, security, usability, compatibility, and reliability. Asks 'how good' rather than 'does it work.' Often expressed as service-level objectives (e.g., response under 2 seconds, support 1,000 concurrent users).

In my work: Performance spot-checks during release windows, usability validation alongside business users, and workflow stability checks. Not formal load testing with dedicated tooling.

Sub-types
Performance Testing
Security Testing
Usability Testing
Compatibility Testing
Reliability Testing
By Visibility: How Much You Know About the Code

Black Box Testing

Proficient

No view into the code. Test purely from inputs and expected outputs.

The tester treats the system as a sealed box: feed in inputs, observe outputs, compare against the spec. Most QA work sits here, especially manual functional and UAT testing. Strong fit for behavior validation; blind to coverage of internal logic.

In my work: Almost all QA work at Accenture falls into this category: testing against requirements and acceptance criteria, no source code access needed.

White Box Testing

Full view into the code. Tests internal logic, branches, paths.

Requires knowledge of the implementation. Includes unit tests, statement coverage, branch coverage, path coverage. Usually owned by developers, sometimes by automation engineers writing structural tests.

In my work: Conceptual knowledge; not part of my day-to-day role.

Gray Box Testing

Partial visibility. Knowing some internal structure to guide smarter tests.

Combines black-box behavior validation with limited knowledge of internals (database schema, API contracts, basic architecture). Common for QA who write SQL queries to verify data integrity or check API responses against known schemas.

In my work: Informally present when I use SQL queries or known SAP table structures to verify backend state during testing.

By Level: Where in the Stack the Test Sits

Unit Testing

Tests a single function, method, or component in isolation.

The lowest level of testing. Cheap, fast, runs in seconds. Typically written by developers as part of their normal workflow and executed automatically on every commit by a CI server. The base of the testing pyramid.

In my work: Developer-owned in my workplaces; not part of my QA scope.

Integration Testing

Proficient

Tests that two or more modules or services work correctly together.

Verifies the wiring between components: an API talking to a database, a microservice calling another, a form submitting to a backend. More expensive than unit tests because real (or near-real) infrastructure has to be running.

In my work: Cross-module business process validation at Accenture with SAP S/4HANA: testing how data flows between modules and how downstream processes react to upstream changes.

System Testing

Tests the entire integrated system as a whole against requirements.

The complete application is exercised end to end in an environment that matches production as closely as possible. Catches issues that only surface when every piece is connected.

In my work: Regression and release cycles at Accenture: full SAP S/4HANA flows and connected web applications tested together before sign-off.

End-to-End Testing

Proficient

Walks through a full user journey from start to finish.

Replicates real user behavior across the full system: log in, navigate, perform a transaction, receive a confirmation. Can be manual or automated. Manual E2E (which is what UAT often is) catches real-world issues; automated E2E is expensive to maintain but valuable in small targeted doses.

In my work: UAT coordination at Accenture: full user journeys validated with business users before go-live. Manual E2E in practice.

Acceptance Testing

Proficient

Formal verification that a system satisfies business requirements.

Often the gate before a release is approved. Requires the whole application to be running. Can include user acceptance testing (UAT, business users) and operational acceptance testing (does it deploy, recover, scale).

In my work: UAT coordination with business users at Accenture, including sign-off cycles before go-live.

User Acceptance Testing (UAT)

Proficient

Real users (or business representatives) confirm the system meets their needs.

The final human check before release. Driven by people who will actually use the software, not by the QA or dev team alone. UAT scripts are usually written in business language, not technical specs.

In my work: Coordinated UAT cycles at Accenture: authored checklists, walked business users through validation, captured sign-off.

By Approach: How the Tests Are Run

Manual Testing

Proficient

Human-driven testing. A real person executes the steps and judges the result.

Indispensable for exploratory, usability, and early-stage validation where automation would be premature or unable to judge nuance. Slower per run but flexible and intelligent.

In my work: Primary mode of work across nearly 3 years: Accenture, HCLTech training, TCL, and portfolio projects.

Automation Testing

Basic, growing

Scripts and tools execute tests repeatedly, faster than humans can.

Best fit for regression, repetitive checks, and CI/CD pipelines. Expensive to write and maintain, especially at UI level, so usually concentrated at lower levels (unit, integration, API) with a few key UI scripts on top. Tooling examples: Selenium, Playwright, Cypress, Postman/Newman for API.

In my work: Selenium with Python at a contributing level: ran existing scripts during regression, triaged failures, suggested adjustments under senior guidance. Postman with JavaScript for API regression. Growing toward independent ownership.

Exploratory Testing

Proficient

Unscripted testing guided by curiosity, intuition, and product knowledge.

The tester explores the application without a predefined script, designing and executing tests on the fly. Often surfaces issues that scripted testing misses because it's not bound by what someone thought to write down. Pairs well with manual exploratory time-boxed sessions.

In my work: Regular practice during release windows at Accenture: following hunches about likely failure modes, especially around recently changed areas.

By Phase: When in the Release Cycle

Smoke Testing

Proficient

Quick health check after a new build. Is it stable enough to test further?

A small set of critical-path checks executed immediately after a deployment or build. If smoke fails, deeper testing is not worth running yet. Fast, broad, shallow.

In my work: Standard practice during Accenture release cycles: quick stability check on a fresh build before full regression.

Sanity Testing

Proficient

Focused check after a small change. Does this specific fix work?

Narrower than smoke. Targeted at the area touched by a recent code change to confirm the fix did what was intended and didn't immediately break the surrounding feature.

In my work: Routine after fix deployments at Accenture: spot check the touched area before opening regression.

Regression Testing

Proficient

Re-runs old tests to make sure new changes did not break existing features.

The biggest insurance policy in software. Every release risks breaking something that used to work; regression catches that. Heavy candidate for automation because the same checks repeat release after release.

In my work: Core part of every release cycle at Accenture: scheduled regression suites across SAP and web applications, with defect triage and re-test loops.

Alpha and Beta Testing

Alpha = internal early testing. Beta = real-world testing with limited users before launch.

Alpha is done inside the team or organization while the product is still rough. Beta opens it to a small group of real users to surface issues that only show up in real environments and usage patterns.

In my work: Conceptual knowledge; not part of my project work to date.
